# Codex job 06 — Recovery and teacher evidence

## Assignment

You are the recovery/evidence engineer working for Claude Code. Preserve student work through the new apprenticeship and make exported evidence truthful and useful. Satisfy **R2, R3, R5, R6 and R7**. Read `docs/claude-codex-team/WORKER_CONTRACT.md` and Claude's task packet before changes.

## Skills

Read `learning-simulation-engine` when locally available. The common contract and this brief remain sufficient if it is absent; report availability honestly. Use `delegate` for scoped reporting, without delegating further.

## Inputs

Inspect current persistence, programme serialization, draft handling, migration fixtures, sample exports and release records. Read the agreed apprenticeship schema and evidence requirements. Establish which browser/profile/origin owns the existing saves and which older formats must remain supported. Do not print or collect personal data.

## Owned outputs

Proposed defaults: `docs/apprenticeship/SAVE_COMPATIBILITY.md` and specifically named tests under `tests/integration/`. Production adapters or `dist/persistence.js` require an explicit activated lease. `dist/opening/programme.js`, entry integration and shared serialization default to Claude ownership. Serialize any handoff involving the simulation engineer: never write the same file concurrently. Propose cross-boundary changes for Claude to apply or reassign.

## Deliverable

Implement the assigned versioned migration, validation or evidence change. Preserve older valid field work while leaving new apprenticeship requirements unearned. Retain actual tests, exact learner explanations, pending oral arrangements, decisions, support use and trainer/learner provenance. Distinguish current state from historic observations and stale results. Never manufacture understanding, activity or truck eligibility during migration.

Keep import validation atomic: a damaged or unsupported file must not replace usable work. Maintain meaningful backup/recovery and multiple-tab ownership behavior. Keep exports local, usable without accounts and free of student names or patient information. Explain browser/profile/device, cleared-storage and export/import limitations in concise teacher-facing text.

## Concrete checks

Test new save/reload; older valid migration; partial draft preservation; export/import round trip; malformed JSON; valid JSON with invalid structure/progression; unsupported version; reset; backup recovery; and competing tabs where the environment permits. Compare exported explanations and observations with what actually happened. Confirm reset and failed import cannot silently destroy unrelated or recoverable work. Register any new test paths with Claude and verify execution.

## Budget and result

One initial implementation plus one focused repair. Investigate a second failure of the same criterion and propose a changed approach. Return status, changed paths, schema/migration decisions, reproducible checks, observed environment, remaining risks and integration steps. Separate automated tests from published-origin and actual school-device observations. Do not publish or alter billing/authentication.
