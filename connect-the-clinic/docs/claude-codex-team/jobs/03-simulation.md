# Codex job 03 — Simulation and progression engineering

## Assignment

You are the simulation engineer working for Claude Code. Extend the existing causal model into the assigned apprenticeship slice. Satisfy **R1, R2, R3, R6 and R7**. Read `docs/claude-codex-team/WORKER_CONTRACT.md` and the task packet before edits. Claude retains architecture and final integration.

## Skills

Read `learning-simulation-engine` when locally available. Use `delegate` for ownership and reporting discipline, without spawning workers. If unavailable, apply this brief and the common contract; report the missing local skill.

## Inputs

Inspect `dist/engine.js`, `dist/opening/programme.js`, current bootcamp and field engines, contracts, migration fixtures and the assigned learning/gameplay requirements. Establish current behavior before replacing it. Read the exact baseline and API decisions supplied by Claude.

## Owned outputs

Proposed defaults: `dist/apprenticeship/engine.js`, `docs/apprenticeship/API.md` and `tests/bootcamp/apprenticeship-engine.test.js`. Only activated task paths may be edited. Shared `programme.js`, core engine, entry files and persistence remain Claude-owned unless leased explicitly for a serialized task. A new module must extend the existing authoritative programme, not introduce a separate state store or completion authority.

## Deliverable

Publish the smallest needed state/action/event/view contract early. Use stable IDs, validated transitions and derived selectors. Reuse existing physical-path, power, address/mask, authorization and stale-test behavior. Model mentor demonstrations separately from learner actions. Mentor responses, staff work and truck eligibility must consume verified events and current model conditions.

Preserve historic work and provenance. Specify versioned serialization and migration requirements for the recovery owner. Reconcile overlapping changes through Claude. Reject invalid actions predictably; do not silently repair learner settings. Document deliberate simplifications and unsupported operations. Do not add WAN, DHCP, DNS or simulated tools merely to make labels look complete.

## Concrete checks

Test a valid and alternative permitted route; disconnected cable; wrong address/mask; relevant repair; stale-result invalidation; changed-cause transfer; demonstration versus practice; skipped dialogue; repeated reward attempts; and truthful truck gating. Check that changing an IP cannot fix a physical disconnection. Include pertinent legacy fixtures and invalid imported progression cases in coordination with recovery.

Use registered test paths or ask Claude to register a new directory: the current `npm test` command enumerates globs. Verify the new tests actually execute. Report automated results separately from browser behavior.

## Budget and result

One initial implementation plus one focused repair. After two failures of the same criterion, investigate and propose a changed approach. Return status, changed paths, commands/results, API changes, migrations, limitations and integration instructions. Do not publish, change unrelated files or create another agent layer.
