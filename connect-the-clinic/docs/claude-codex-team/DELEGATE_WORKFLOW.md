# Delegate workflow for this project

This portable project runbook applies the teacher's existing **Delegate — Teaching Studio** skill to the explicit request: **Claude Code leads; Codex supplies the specialist workers**. It is not a replacement global skill, an installed plugin or a provider bridge.

If Delegate is available in the local Claude session, load it and its applicable runtime guidance. If available to a Codex worker, use the relevant specialist guidance within the assigned job; do not let the generic coordinator instructions create another team. The explicit project assignment governs roles. The stock same-provider worker defaults are not the route requested here.

If the skill is absent from that machine, read this runbook and the role contracts directly. Do not claim that a skill listed in ChatGPT is installed in Claude Code. The package is self-contained enough to proceed without installing a new orchestration service.

## Lead responsibilities

Keep Claude responsible for the user objective, learning validity, architecture, creative direction, integration and acceptance. Inspect existing work and authoritative inputs. Preserve current changes, access controls and the user's subscription constraint. Verify actual available tools, model controls and client versions; record unknown values as unknown.

Define the smallest complete, observable learner loop and its evidence. Identify which decisions need a shared contract now. Make routine reversible choices without creating unnecessary permission gates. Keep formal curriculum mappings separate from proposed I-can statements and observed learner evidence.

## Small, bounded team

Start at most two independent workers. Do not run seven jobs just because seven briefs exist. Sequence work that needs unfinished contracts or touches a shared file. Use a fresh reviewer after material output exists. Keep one delegation layer; specialists escalate requests for help to Claude.

One file has one active owner. Before using worktrees, establish the correct starting revision and how relevant uncommitted work reaches them. Keep credentials and unrelated private material out of packets. A behavioral file allowlist is not an operating-system sandbox; use the supported isolation and permissions already available.

## Executable assignments

Each packet specifies one objective; requirement IDs; source/version; exact owned paths; read scope; forbidden changes; shared interfaces; dependencies; outputs; checks; bounded initial attempt and one focused repair; escalation conditions; and report format. See `TASK_TEMPLATE.md`.

Use a genuinely supported worker launch from `CODEX_BRIDGE.md`. Retain the task file, process outcome and returned artifact. Do not claim a Codex invocation, model switch, completed test, generated asset or background job merely because it was requested.

## Integrate the representative sample first

The first shared sample is the complete mentor-supported site interaction, not seven separate design documents. Freeze only the minimum event/view/asset contract needed to build it. Inspect the real files and running behavior. Then expand the accepted conventions across the other visits.

Require `complete`, `partial` or `blocked`, changed paths, observed checks, known gaps and integration notes. Read the changes rather than accepting a confident summary. Resolve conflicting claims with tests, source evidence or direct observation.

## Quality and repair

Use the R1–R7 gates in `WORKER_CONTRACT.md`. Independent QA receives the raw task, contracts, sources and integrated artifact, without the builder's confidence as a starting conclusion. Its findings require reproducible evidence and an inspected scope.

Return a failed criterion with concrete evidence for one focused repair. If it fails again, investigate assumptions, dependencies or the interface and change approach. Continue other useful authorized work. Do not treat a worker budget as permission to abandon the user's objective.

## Records and completion

Keep one short `docs/apprenticeship/RUN.md` with ownership, decisions, checks, gaps and next action. Existing API docs, asset manifest and test reports remain the authoritative details. Do not duplicate a large tracking system.

Record actual runtime/model/effort when visible. Do not infer dollar savings, credit consumption or entitlement from a prompt. Respect existing release authority. Deliver a playable result, real access route and honest limitations; local completion is not deployment or school validation.
